You already have data and you already have Python. What NumPy adds is a shape to put the data in — so you can do maths to the whole thing at once instead of picking at it one item at a time.

00 / START HERE

What NumPy is actually for

Most courses drop you straight into the commands without ever saying why the thing exists. So before anything else: here is the job NumPy does, and why you would want it done.

You can already hold data in Python. Lists, dictionaries, lists of dictionaries — you have been doing it for a while now and it works. But look at what you actually do with it. You loop. You reach in, pull one item out, test it, do a sum on it, put the answer somewhere, go back for the next one. Every question you ask of the data becomes a small machine you have to build by hand, and the more numbers there are the more that starts to hurt.

That is fine for twenty records. It is miserable for twenty thousand, and the code that does it is long, fiddly and full of places for a mistake to hide.

What NumPy does is take that pile and give it a shape. It turns loose, messy, real-world numbers into one structured object — a thing with known dimensions that Python can work on as a whole rather than one item at a time. Once the data has a shape, you stop writing machines. You state what you want and NumPy does it to everything at once.

Think of it as a pre-digester. Raw data arrives lumpy and awkward. NumPy breaks it down into something regular enough that Python can absorb it without chewing through a thousand lines of code first. Everything downstream — pandas, charting, statistics, machine learning — is standing on this. A pandas DataFrame is NumPy arrays underneath with names written on the side.

That is the whole pitch. Messy reality in, one tidy structured object out, and maths you can do to all of it in a single line. The rest of this guide is about what that shape is, how to read it, and what happens when you put two of them together.

Now: boxes inside boxes

To make sense of the shape, three pictures. These are the ones everything else hangs off, and if you have them straight then NumPy stops looking like a pile of strange punctuation.

Picture one

A box

A variable is a box with a label on it. Put something in, read it back out. That is the whole idea and it does not get more complicated.

Picture two

Boxes inside boxes

A box can hold other boxes. Those can hold others again. This is how Python builds anything complicated — not with new ideas, just with more layers of the same one.

Picture three

An address

To reach something buried three layers down you write its address, one layer at a time. Each set of brackets is one more line of the address.

That third one is worth dwelling on, because it is the bit that looks frightening and isn’t. Writing arr[2][1][3] is not a magic incantation. It is a postal address, read the way you’d read one aloud:

Now the third picture: sheets in a book

Boxes inside boxes gets you a long way, but it goes a bit vague once you’re three layers down. Here is a sharper version for arrays specifically, and it is the one to keep.

Think of sheets of paper. One sheet has rows and columns ruled on it — an ordinary table, the sort you’d draw by hand. That is a two-dimensional array, and it is the thing at the centre of everything else.

Now stack several sheets and bind them. You have a book. Each sheet keeps its own rows and columns exactly as before — nothing about a page changes because you put other pages behind it. But now there is one extra thing you have to say before you can point at a cell: which page.

One sheet

Rows and columns

A table. Two numbers get you to any cell: which row, which column. arr[1, 2]

A book

Pages of tables

Three numbers now. Which page, then which row, then which column. arr[0, 1, 2]

A shelf of books

And so on, for ever

Four numbers. Which book, which page, which row, which column. The pattern never changes — you just say one more thing at the front.

This is why the numbers in a shape read outside in. A shape of (3, 5, 4) means three pages, each with five rows, each row holding four values. Biggest container first, smallest last. Same order as the address. Same order as everything else in this guide.

One honest wrinkle, and then we can get on. Underneath, NumPy does not really keep separate sheets. It keeps one long unbroken run of numbers and remembers a rule for folding it into pages. You will never see that and it will never bother you — but it explains why reshaping an array is instant. Nothing gets moved. NumPy just changes its mind about where the page breaks go.

01 / THE TRADE

An array is not a list

A Python list will hold anything you shove in it. A NumPy array flatly refuses. That refusal is the entire point, and everything else follows from it.

Here is the difference, and it is worth understanding properly rather than taking on trust.

A list does not really hold your things. It holds a row of addresses — little notes saying where each thing has been put. The things themselves are scattered all over memory, and they can be anything: a number here, a string there, another list over there. Wonderfully flexible. Also, to add one to every number in it, Python has to go to each note, walk to wherever it points, work out what kind of object it has found, decide what “add one” even means for that kind of object, do it, and put the answer somewhere. Once per value. The working out is the slow part, and it happens every single time even though the answer is identical.

An array makes one trade. Every value must be the same type. Once that is guaranteed, the values can sit end to end in a single unbroken block. No notes. No walking. No working out what anything is, because it was stated once at the front and applies to all of them.

Scroll sideways to see both halves →

What you get 01

Maths on the whole thing

arr * 2 doubles every value. No loop written, no loop visible. This is called vectorisation and it is the reason NumPy exists at all.

What you get 02

Free reshaping

The values are one flat run. The shape is a note on the side saying where the page breaks go. Change the note and you have changed the shape — without moving a single number.

What it costs

Types get enforced quietly

Put an integer next to a float and the integer becomes a float, because the array can only carry one type. Nothing warns you. Check .dtype early.

import numpy as np

source_values = [8, 8.5]
values_array = np.array(source_values)

values_array         # array([8. , 8.5])
values_array.dtype   # dtype('float64')

The 8 has quietly become 8.0. NumPy picked float64 because it was the one type that could hold both values without throwing anything away. It will not mention this to you, and it is a common reason a result looks wrong later for no obvious cause.

A listYou describe the journey
result = []
for value in values:
    result.append(value + 1)
An arrayYou describe the destination
result = arr + 1

That is the shift. You stop writing down the steps and start writing down what you want to be true at the end. Hold onto it, because when axis turns up in section 06 it only makes sense if you have stopped worrying about which element is being visited when.

Where this comes from

Hollerith’s cards, 1890

The 1880 United States census took eight years to count by hand. With the population climbing, the Census Bureau faced the genuinely absurd prospect that the 1890 count would not be finished before the 1900 one was due to start. A Bureau employee called Herman Hollerith suggested punching holes in stiff cards to represent each person, then running the cards through a machine that closed an electrical circuit wherever a hole let a pin drop through.

The 1890 count came in inside two years. But the thing we inherited was not the machine, it was the card. Every card the same size. Every field in a fixed column. Every record built identically to every other one, whether or not it had anything interesting to say. Rigid, uniform, positional — the same three demands a NumPy array makes today. Hollerith’s company eventually became part of IBM.

Where this comes from

Iverson’s notation, 1962

Kenneth Iverson was a Harvard mathematician who decided the problem with describing computation was not the computers but the handwriting. In 1962 he published A Programming Language, in which operations applied to whole arrays as single acts. Adding two tables together: one symbol. Summing a column: one symbol. The loop was not optimised away, it was never written, because the notation gave it nowhere to live.

The language became APL and it was gloriously mad — it needed its own typeface of Greek and geometric symbols, and programs were frequently unreadable to everyone including the person who wrote them last Tuesday. The core idea survived anyway. Whole-array operations, the business of making differently shaped arrays fit each other, and naming a direction to work along all come from APL. NumPy is what happened when those ideas grew up and got a job.

02 / SHAPE

Pages, rows and columns

A shape is a list of numbers in brackets telling you how the thing is built. Biggest container first, smallest last. That is it — but it is the single most useful thing to know about any array, so it is worth getting comfortable.

Back to the book. One sheet has rows and columns. Stack sheets and you get pages. Stack books and you get a shelf. Every time you add a layer you say one more thing at the front, and the thing at the centre — the ordinary table with rows and columns — never changes.

Scroll sideways for the full progression →

The four things to ask an array

No brackets on any of these

These are facts about the array, not jobs it does. Putting brackets after them gets you something baffling rather than an answer.

.shapeHow it’s built, as a tuple. Check this constantly.
.ndimHow many layers — how long the shape tuple is.
.sizeHow many values in total, the shape multiplied out.
.dtypeWhat kind of thing is stored in every slot.
Worth keeping to hand

All three at once

Print this whenever an array surprises you. It answers what’s in it, how it’s built, and how it’s stored, in one go.

print(
    f"* Array:\n {arr} \n\n"
    f"* Shape: \n {arr.shape} \n\n"
    f"* Type:  \n {arr.dtype}"
)

The f makes the curly braces live. The \n pairs put a blank line between sections. Neither touches the array — only the printout.

A shape tells you the furniture, not what’s on it. (3, 4) means three rows of four. It has no idea whether that’s three shops with four quarters of takings, or four shops with three. Only you know which way round you built it, and NumPy will never think to ask.

Reshaping: the only rule is that the count must match

Reshaping refolds the same values into a different arrangement. Nothing is created, nothing is thrown away, so the total has to come out the same. Thirty values can become three rows of ten, or six rows of five, or three pages of two rows of five — all of those multiply to thirty. They cannot become four rows of eight, because that is thirty-two and you are two values short.

arr = np.arange(30)

arr.reshape(3, 10)      # 3 rows of 10
arr.reshape(3, 2, 5)    # 3 pages, each 2 rows of 5
arr.reshape(3, -1)      # -1 means "you work it out"  ->  (3, 10)
arr.reshape(-1, 5)      #                             ->  (6, 5)
arr.reshape(-1)         # flat again                   ->  (30,)

The -1 is you telling NumPy to do the arithmetic. It works whenever the division comes out whole, and refuses when it doesn’t — arr.reshape(4, -1) on thirty values fails, because thirty does not go into four. Check arr.size first and the possible shapes are just the ways that number can be grouped.

Where this comes from

The Fortran argument, 1957

When you write a table into one long run of memory, somebody has to decide which way to unroll it. Fortran, released by IBM in 1957 for numerical work, went down the columns — all the way down the first, then start the second. C, arriving in the early seventies with different priorities, went across the rows.

Neither is wrong. The difference is invisible right up until you connect two systems that disagree, at which point your data comes out transposed and you spend an afternoon finding out why. NumPy uses C order by default and still carries an order argument on reshape() and flatten(), where 'C' means rows-first and 'F' means columns-first. If you ever meet order='F' and wonder what the F is doing there — it is a scheduling decision made at IBM before the integrated circuit was invented.

03 / REACHING IN

Getting the values back out

Square brackets, one address per layer, commas between them. The addressing is easy once you have seen it. Slicing is the bit that looks like line noise the first time and turns out to be three simple ideas, so we’ll do those properly.

arr[row, column]                 # one sheet
arr[page, row, column]           # a book
arr[book, page, row, column]     # a shelf

Same as the postal address in section 00. Widest thing first, narrowest last, and the value you want falls out of the end. A colon means all of them in that position — it doesn’t remove the position, it fills it with “everything”.

arr[3, :]      # row 3, every column
arr[:, 3]      # every row, column 3
arr[0, :, 2]   # page 0, every row, column 2

Slicing, slowly

A slice is a range instead of a single position. It has the form start:stop, and there are exactly three things to know about it.

Thing one

Counting starts at nothing

The first item is number 0, not number 1. Everyone hates this for about a fortnight and then stops noticing.

Thing two

The stop is not included

1:4 gives you 1, 2 and 3. It stops before 4. Think of it as “up to but not including”, the way a shop is open 9 till 5 and shut at 5.

Thing three

Minus counts from the back

-1 is the last item, -2 the one before it. It does not reverse anything — it only changes which end you count from.

Scroll sideways for both directions →

Slices in more than one direction

The comma keeps the directions separate, so you can slice each one independently. Read each side on its own and then put them together.

arr[1:3, -2:]

#  1:3   ->  rows 1 and 2      (stop 3 is excluded)
#  -2:   ->  the last two columns
#  together: a rectangular block cut out of the sheet

And with a book, the same again with one more address on the front:

arr[1:2, -3:-1, -3:]

#  1:2    ->  page 1, kept as a slice rather than picked out
#  -3:-1  ->  the third and second rows from the end
#  -3:    ->  the last three columns
#  result shape: (1, 2, 3)

First address, second address, third address — and what you’re holding at the end is the package. If you can read a slice one comma at a time, out loud, in plain English, you can read any of them. The complicated-looking ones are just three simple ones standing next to each other.

One number takes a layer off. A slice keeps it.

This catches everyone, and it matters more than it looks like it should.

A warning: slices are windows, not photocopies

Slice a Python list and you get a new list. Slice a NumPy array and you usually get a view — a window onto the same values. Write through the window and you have changed the original.

arr = np.arange(10)
chunk = arr[0:3]
chunk[0] = 99

arr    # array([99, 1, 2, 3, 4, 5, 6, 7, 8, 9])
       # the original changed, and nobody mentioned it

This is on purpose, and it is one of the reasons NumPy is quick. Slicing a million-row array costs nothing, because nothing is copied. The price is that an innocent-looking working variable can be wired straight into your source data.

The habit: if you’re going to change it, copy it first. If you’re only reading, the window is free and better.

working = arr[0:3].copy()

Where this comes from

The years of two libraries, 1995–2006

Arrays reached Python in 1995 in a package called Numeric, written largely by Jim Hugunin. It worked well enough at modest sizes. By the turn of the century a group at the Space Telescope Science Institute, wrangling Hubble images, found it fell over at the sizes they needed and wrote a replacement called numarray. numarray was better with big arrays and worse with small ones.

So the scientific Python world spent several years split down the middle, with two incompatible array libraries, two sets of followers, and no way to read each other’s code. In 2005 Travis Oliphant took Numeric, rebuilt it with numarray’s strengths folded in, and released NumPy in 2006. Everyone came back together within a couple of years.

Two things survive from that. Anything written before 2006 refers to libraries that no longer exist, so if a tutorial mentions Numeric or numarray by name it is at least twenty years out of date and you should close the tab. And the merge is why NumPy occasionally offers you two functions that do almost exactly the same thing.

04 / FILTERING

Asking a question of everything at once

This is where NumPy starts earning its keep. Compare an array to a value and you don’t get one answer — you get an answer for every element, in an array of True and False the same shape as the original. That thing is called a mask, and once you have one you can point it at anything.

Start with what it saves you. Here is the same job done twice: keep only the values over four, and average them.

Plain PythonEight lines and a decision
kept = []

for value in values:
    if value > 4:
        kept.append(value)

total = 0
for value in kept:
    total = total + value

average = total / len(kept)
NumPyOne line, no decision
average = arr[arr > 4].mean()

Both do the identical work. The difference is that in the left-hand version you are supervising every step — setting up an empty box, walking the collection, testing each item, deciding whether to keep it, then walking the results again to add them up. In the right-hand version you state the condition and the answer you want, and go and put the kettle on.

And it scales. Add a second condition and the left-hand version grows another branch. The right-hand version grows five characters.

How the mask actually works

arr = np.array([2, 7, 4, 19, 5])

arr > 4        # array([False,  True, False,  True,  True])
arr[arr > 4]   # array([ 7, 19,  5])

The first line does the comparing. The second puts that True-and-False array inside the original array’s brackets, and NumPy walks the two together keeping everything the mask approved of. The result normally comes back as a single row, because the survivors of a condition rarely form a tidy rectangle.

You have met this before, in pandas. df[df["price"] > 4] is doing exactly this: the inner bit makes a column of True and False, the outer brackets keep the rows where it said True. A pandas Series is a NumPy array with labels bolted on, so filtering a DataFrame is this same machinery wearing a nicer coat.

The useful trick: build a mask from one array, aim it at another

Nothing ties a mask to the array that made it. It is just True and False in a particular shape, and any array of that shape will take it.

Scroll sideways for the full picture →

temperature = np.array([12, 27, 31, 18, 24])
sales       = np.array([340, 890, 1120, 410, 700])

hot = temperature > 25
sales[hot]              # array([ 890, 1120])
sales[hot].mean()       # average takings on the hot days
More than one condition

Symbols, not words

arr[(arr > 4) & (arr <= 17)]   # both
arr[(arr <= 5) | (arr > 15)]   # either
arr[~(arr > 4)]                # not
Two things that will bite

Brackets, and vocabulary

Every comparison needs its own brackets. & grabs tighter than > does, so without them Python groups the expression wrongly and the error message will send you somewhere useless.

The words and and or will not work. They want one yes-or-no answer and you have handed them five thousand. The message — “the truth value of an array with more than one element is ambiguous” — means: you used a word where a symbol was needed.

One last small thing. The condition inside the brackets has to name the same array the brackets belong to. Once your working variable is macro_arr, an old arr left behind in the condition will either error or, far worse, quietly filter against the wrong data and say nothing.

macro_arr[(macro_arr <= 1) | (macro_arr > 9)]
05 / COMBINING

Two arrays, laid over each other

Everything so far has been about one array. Real work involves several. The syntax for combining them is about four characters long, which is exactly the problem — there is almost nothing on the page to tell you what NumPy has decided to do.

Start with the easy case. Two arrays the same shape, added together.

a = np.array([[1, 2, 3],
              [4, 5, 6]])

b = np.array([[10, 20, 30],
              [40, 50, 60]])

a + b     # array([[11, 22, 33],
          #        [44, 55, 66]])

Top-left meets top-left. Bottom-right meets bottom-right. Every arithmetic operator behaves this way and so does every comparison — a > b hands you a mask of which cell beat which.

NumPy pairs things up by position. It has no idea what anything is called.

Join two DataFrames in pandas and the labels do the work — the row for Leeds finds the row for Leeds wherever it happens to be sitting. NumPy arrays have no labels at all. Row three meets row three because they are both row three. That is the entire matching logic.

So if one array came out of a database sorted by date and the other out of a spreadsheet sorted alphabetically, NumPy will cheerfully pair them up anyway, hand you a result of exactly the right shape, and say nothing whatsoever. It will look perfect. This is the mistake that ends up in reports.

When the shapes don’t match: broadcasting

Arrays don’t have to be the same shape. NumPy will stretch a smaller one across a bigger one if the shapes are compatible. You have done this already without noticing — arr * 2 is one lonely number stretched across the whole array.

Scroll sideways for the rule →

# works
(4, 3)     with  (3,)      -> (4, 3)     row stretched down
(4, 3)     with  (4, 1)    -> (4, 3)     column stretched across
(2, 3, 4)  with  (3, 4)    -> (2, 3, 4)  one sheet used on every page
(4, 1)     with  (1, 3)    -> (4, 3)     both stretch; a grid appears

# doesn't work
(4, 3)     with  (4,)      -> error: 3 and 4 are neither equal nor 1
(4, 3)     with  (2, 3)    -> error: 4 and 2 are neither equal nor 1

The one that catches everybody

Look at the two failures. Adding a row of three to a four-by-three table works fine. Adding a column of four to the same table fails — even though four is precisely how many rows it has. That feels wrong, and here is why it isn’t.

col = np.array([10, 20, 30, 40])   # shape (4,)

col.reshape(4, 1)                  # (4, 1) — spelt out
col.reshape(-1, 1)                 # (4, 1) — same, without counting
col[:, np.newaxis]                 # (4, 1) — the usual way people write it

table + col.reshape(-1, 1)         # works now

np.newaxis is just the word None wearing a name badge. Put it in the brackets and it inserts an empty dimension at that spot. col[:, np.newaxis] reads as: keep everything in the first direction, then add a second direction with one slot in it.

Reading the error. ValueError: operands could not be broadcast together with shapes (4,3) (4,)

“Operands” means the two things either side of the plus sign, listed in the order you wrote them. Line the shapes up on the right and find the column that fails. That is the whole diagnosis, and it takes about four seconds once you know to do it. Whenever a broadcast fails, print both shapes before you do anything else — it is either a real mismatch in your data or a flat (n,) that wanted to be (n, 1), and only you can tell which.

Picking between two arrays with np.where

A mask tells you which positions pass. np.where uses a mask to take a value from one place where it’s True and another place where it’s False. It is an if/else applied to everything at once — and unlike masking, it keeps the shape. Nothing is dropped; every slot gets filled from one side or the other.

np.where(condition, use_this_if_true, use_this_if_false)

sales = np.array([340, 890, 1120, 410, 700])

np.where(sales > 500, "good", "poor")
# array(['poor', 'good', 'good', 'poor', 'good'])

np.where(sales > 500, sales * 1.1, sales)
# bump up the good days, leave the rest alone
Masking

arr[mask] throws away

The failures are dropped. You get back something smaller, usually a single row. Use it when you only want the ones that qualified.

Where

np.where(mask, a, b) swaps out

The failures get replaced. You get back the same shape you started with. Use it to label, cap, or patch things in place.

Getting several arrays into one place

None of the above is any use until you have arrays to combine. Three functions cover nearly everything. Note the arrays go inside a list — each function takes one argument that happens to be a sequence, hence square brackets inside the round ones.

CallWhat it doesWhat it needs
np.vstack([a, b])Stacks them as rows. The table gets taller.The same number of columns.
np.hstack([a, b])Puts them side by side. The table gets wider.The same number of rows.

Stacking is the moment the risk gets baked in. The second you stack two arrays together you have declared that their positions line up. Nothing has verified that. From then on, every calculation you do rests on it.

If the two sources could possibly be in different orders, sort them into a known order first, or do the join in pandas where the labels can be checked. It is ten minutes now against a wrong number in a report later.

06 / AXIS

What on earth is an axis?

This word causes more confusion than anything else in NumPy, and mostly because you already know it from somewhere else. Let’s deal with that first, before any rules.

What you already think an axis is

You learned axes at school. The x axis goes across the bottom. The y axis goes up the side. They are directions on a picture, they have letters, and there are two of them because a piece of paper is flat.

That is a perfectly good idea and it is not the one NumPy is using. Which is why the word keeps not quite fitting.

What NumPy means by it

In NumPy an axis is one of the layers in your shape. Not a direction on a graph — a level of the structure. And instead of letters they get numbers, because there might be five of them and we ran out of alphabet somewhere around the second one.

Go back to the book. A shape of (2, 3, 4) has three layers: pages, then rows, then columns. Those three layers are the three axes, and they are numbered in the order they appear in the shape.

Axis 0

The pages

The first number in the shape. The outermost layer — the biggest container.

Axis 1

The rows

The second number. One layer further in.

Axis 2

The columns

The third number. The innermost layer — the actual run of values.

So “axis” is just a numbered name for a layer. Axis 0 is always the outermost one. The last axis is always the innermost run of values. On an ordinary flat sheet, shape (3, 4), there are only two: axis 0 is the rows and axis 1 is the columns. Same as reading the shape left to right, which you have been doing since section 02.

Why it matters at all: when you total something up, NumPy needs to know which layer to do the totalling through. Add up the whole thing? Add up each column separately? Each row? Each page? You answer that by naming a layer — and naming a layer means giving its number.

Now the actual rule

Here it is, and it is mechanical enough that you never have to think about it again:

The axis you name is the one that disappears.Find its number in the shape, delete it, and what’s left is your answer’s shape

A (3, 4) array summed along axis 0: delete the 3, you’re left with (4,) — four numbers, one per column. Summed along axis 1: delete the 4, you’re left with (3,) — three numbers, one per row. That’s it. It works the same at any number of layers.

Scroll sideways for both directions →

np.sum(arr, axis=0)      arr.min()        arr.argmin()
np.mean(arr, axis=0)     arr.max()        arr.argmax()
np.std(arr, axis=0)      arr.cumsum()     np.median(arr, axis=0)

Most of these take an axis and most exist in two forms — np.sum(arr) and arr.sum() are the same thing. The arg pair is worth a mention: argmax tells you where the biggest value is, not what it is. You then normally use that position to look something up in another array — which drops you straight back into the positional-matching problem from section 05.

Collapse, then put it back — the loop most analysis goes round

Squash the array down one direction, then lay the result back over the original. Almost every normalisation, centring or share-of-total calculation is this shape, and it is where sections 05 and 06 shake hands.

Squash it

Average along one direction. A (4, 3) table averaged along axis 0 becomes a (3,) row of column averages. The rows are gone.

Look at the shape

A (3,) lines up neatly under a (4, 3). A (4,) does not. Check now, not after the error message.

Lay it back over

Subtract it, divide by it, compare against it. The small array stretches to cover the big one and every value gets measured against its own column.

readings.shape                      # (4, 3)

column_means = readings.mean(axis=0)
column_means.shape                  # (3,)   the rows have gone

centred = readings - column_means   # (4, 3) with (3,) — lays straight back over

Squash the other way and the return trip breaks, because you get a flat (4,) and lining up on the right puts the 4 under the 3. Same trap as figure 08.

row_means = readings.mean(axis=1)   # shape (4,)

readings - row_means                # ValueError — 3 against 4
readings - row_means.reshape(-1, 1) # works

Or just ask for the layer to be kept. readings.mean(axis=1, keepdims=True) gives you (4, 1) instead of (4,) — it leaves a 1 where the squashing happened, so the result lays straight back over the original with no fiddling. That is the entire purpose of keepdims and it is why it exists.

07 / THE MATHS

What the functions are for

These all apply to every value and keep the shape. This is not a maths course — it’s enough to know why you’d reach for each one and what it does to a pile of numbers.

Logarithms: squashing the big end

A logarithm answers one question: what power do I raise this number to, to get that number? In base ten, the log of 1,000 is 3, because ten times ten times ten is a thousand. That is genuinely all it is.

The useful bit for you is what it does to a set of numbers. A log squashes the big end of the range and spreads out the small end.

CallBaseReach for it when
np.log1010A human has to read it. Each step of 1 means ten times bigger. Best for charts.
np.log22Doublings matter. Common in computing, and anything measured in halvings.
np.loge, about 2.718The default, and the one every statistics formula assumes. Growth and decay.
np.exp—The opposite of np.log. Undoes a natural log, or models compounding growth.

e is not a NumPy thing and it is not a fallback for anything. It is a fixed number, roughly 2.71828, that shows up whenever something grows in proportion to how much of it there already is — compound interest, populations, radioactive decay. Logs to base e get called natural logs for that reason, which is a slightly grand name for a very ordinary constant.

Two things a log will not do for you. The log of zero is undefined — you get -inf and a warning. The log of a negative number gives you nan.

Since count data is usually full of zeros, the standard dodge is to shift everything up by one first: np.log(values + 1). NumPy gives you np.log1p() which does exactly that, more accurately.

Where this comes from

Napier’s twenty years, 1614

John Napier was a Scottish laird at Merchiston Tower with an interest in mathematics and a much larger one in theology. He spent about twenty years building a table. The problem he was attacking was brutally practical: astronomers and navigators spent most of their working lives multiplying long strings of digits by hand, and every one of those was a chance to make a mistake nobody would notice until a ship failed to turn up.

His idea was that if you write down the exponents, multiplication turns into addition. Look up two numbers, add them, look the answer back up. Two lookups and a sum instead of a page of long multiplication. When the tables reached Kepler his workload dropped so far that the Rudolphine Tables — the planetary calculations behind his laws of motion — became finishable at all. Laplace later said logarithms had doubled the lifespan of the astronomer, which is only a mild exaggeration.

The slide rule turned up within a decade and stayed the working engineer’s tool for the next three hundred and fifty years, until pocket calculators killed it off. That logs are still on your chart axes is a happy accident — something invented to make arithmetic smaller turned out to make lopsided data smaller too.

Two kinds of random, and why they’re different

A distribution is just a description of which values are likely and which are rare. Two of them matter for everyday work, and the difference between the two functions is not a detail you can skip.

np.random.rand(3, 4)                  # flat, between 0 and 1
np.random.uniform(10, 50, size=5)     # flat, bounds you choose

np.random.randn(100)                  # bell curve, average 0, spread 1
np.random.normal(70, 5, size=100)     # bell curve, middle and spread you choose

np.random.seed(42)                    # same "random" numbers every run

np.random.seed() pins down where the generator starts, so you get the same values every time you run it. It controls nothing else — not the range, not the size. Set it when somebody else needs to reproduce your results.

Average and middle, and when they part company

The mean adds it all up and divides. The median sorts everything and takes the one in the middle. On tidy symmetrical data they agree. On lopsided data they can end up in different postcodes, because one enormous value drags the mean hard and barely moves the median.

salaries = np.array([24000, 26000, 27000, 29000, 310000])

np.mean(salaries)     # 83200  — describes nobody in this list
np.median(salaries)   # 27000  — describes four of the five

The gap between them is itself a useful signal. If the mean and the median are miles apart, your data is lopsided — which is also your hint that a log might be worth taking before you chart it. np.std() gives the standard deviation, the typical distance from the average, and it inherits the mean’s weakness for being bullied by extremes.

nan: the value that isn’t one

nan means “not a number”. You get one when a sum has no sensible answer — the square root of a negative, zero divided by zero — and wherever data is simply missing.

np.sqrt(np.array([4, -9, 16]))    # array([ 2., nan,  4.]) and a warning
01

It spreads

One nan anywhere makes np.sum() and np.mean() return nan for the lot. Use np.nansum(), np.nanmean(), np.nanmax().

02

It fails every test

nan == nan comes back False. You cannot find missing values by comparing. Use np.isnan(arr), which hands you a mask.

03

It’s a float

An integer array has to become a float array to carry one. A very common reason for a dtype changing when you didn’t ask it to.

04

All of that is deliberate

Every annoying thing about it was designed in on purpose, forty years ago, by people who had thought about it a great deal.

Where this comes from

IEEE 754, 1985

Before the mid-eighties every manufacturer did decimals their own way. The same program on two different machines could give two different answers, and a calculation that overflowed might crash, wrap round to a negative, or quietly return nonsense, depending entirely on whose hardware you happened to be sitting at. Numbers were not portable in any useful sense.

A committee got together in 1977, with the mathematician William Kahan doing much of the design, and after eight years of arguing produced IEEE 754. It fixed how a decimal number is laid out in bits, and set aside particular patterns for things that are not ordinary numbers: infinity, negative infinity, and Not a Number.

Kahan’s argument for nan was that one failed sum should not kill a long calculation — but it must never be mistakable for a real answer either. So it had to spread, contaminating everything downstream until somebody dealt with it properly. Its refusal to equal itself comes from the same reasoning: it fails every comparison, so no test can accidentally wave it through. Everything irritating about nan is the safety feature working. And float64 is that standard’s double-precision format, unchanged since 1985.

Broadcasting check

Three steps, every time

1. Write both shapes down, lined up on the right.

2. Each column must match, contain a 1, or be missing.

3. The answer takes the bigger number from each column.

A flat (n,) counts as a row. If you meant a column, make it (n, 1).

Axis check

Cross it out and look

An axis is a layer, numbered from the outside in. Axis 0 is the outermost. The last axis is the run of values.

The one you name is the one that disappears. Cross its number out of the shape and read off what’s left. Add keepdims=True to leave a 1 there instead.
